# Telegram CV retrieval, version 1

This checkpoint lets a recruiter explicitly choose one referenced Telegram PDF/DOCX attachment for a private candidate draft. It retrieves original bytes on the Mac, uploads bounded binary to the host, and uses the existing private CV storage/validation. It never chooses between multiple files automatically, replaces an existing CV, attaches to a reviewed draft, or gives the Mac database/storage credentials. Filename/type detection is not a malware scan or a complete document-structure validation.

All APIs use TELEGRAM_INTAKE_ENABLED. Staff APIs require MFA and candidates.read, candidates.write, documents.write; mutations enforce Origin. Every worker phase rechecks those current owner permissions, scoped worker token, connected worker/account/generation/connection lease, and job-specific fences. Revoked permissions or a different Telegram account cannot access or attach the file.

## Staff and UI

GET /api/staff/telegram-cv?draftId=UUID[&after=cursor] returns `{draftId,documentRevision,cv,canRetrieve,connectionIssue,attachments,jobs,nextAfter}`. `cv` is null or `{filename,status:"validated"}`. ConnectionIssue is null or `CONNECTION_REQUIRED|ACCOUNT_MISMATCH`; canRetrieve additionally requires an open draft, no current CV and document permission. Each attachment independently indicates account eligibility. Draft rows now expose `documentRevision`, a counter that changes only when their document changes; ordinary field edits do not change it.

Attachments are at most 50 rows, `{extractionJobId,messageId,attachmentIndex,filename,mimeType,sizeBytes,documentId,eligible,reason}`. Reason is null or `UNSUPPORTED_FILE|FILE_TOO_LARGE|SOURCE_UNAVAILABLE|CONNECTION_REQUIRED|ACCOUNT_MISMATCH|DRAFT_CLOSED|CV_EXISTS`. Eligible requires a concrete source document ID, document media kind, PDF/DOCX filename, known size absent or 1–4194304, and the same currently connected account. This is only retrieval eligibility, not validated CV status. Attachment cursor is `extractionJobUUID:messageId:attachmentIndex`, ordered lexically by that tuple (messageId compared numerically), exclusive. `nextAfter` is null or that cursor. All attachment suggestions are inspectable; no hidden unbounded select-all.

Jobs contains the active retrieval first (if any), followed by the most recent other jobs, at most 20 total. Each row is `JobSummary={id,draftId,status,errorCode,attempts,availableAt,updatedAt,source,completion,canRetry}`. Status `queued|leased|waiting|failed|cancelled|completed`; source is the immutable Source below. Completion is null or the success receipt below. The UI must keep manual upload available and explicitly explain that a listed attachment has not yet been retrieved/validated. Refresh document state after completion without overwriting unsaved profile edits.

POST /api/staff/telegram-cv:

* `{action:"retrieve",draftId,expectedDocumentRevision,extractionJobId,messageId,attachmentIndex}` → `{job:JobSummary}`. No draft-version guard: field edits may continue. Server resolves the referenced private attachment and current connected account. At most one active retrieval per draft; repeating the same active selection is idempotent; choosing a different attachment requires cancel first. An existing CV always rejects retrieval.
* `{action:"cancel",jobId}` → `{job:JobSummary}`. Fences further upload/attachment, keeps any uncertain private object in the cleanup queue.
* `{action:"retry",jobId}` → `{job:JobSummary}`. Only failed/cancelled jobs with unchanged empty document and same Telegram account can retry. Refreshes connection generation, resets five-attempt budget; never switches source or silently replaces a CV. A connection-generation change is visible as failed CONNECTION_CHANGED when status is read; retry explicitly binds the current generation.

## Worker protocol

POST /api/telegram-cv/worker/{claim,defer} JSON uses bearer token and no Origin. Common Proof is `{connectionId:UUID,generation:positiveInteger,connectionLeaseToken:UUID,accountUserId:positiveDecimalString}` (same values as history protocol). Claim body is Proof. Response `{job:null,retryAt:ISO|null}` or `{job:{id,leaseToken,leaseExpiresAt,sourceDigest,source},retryAt:null}`. Source is `{extractionJobId,chatId,accountUserId,peer:{kind,id},messageId,attachmentIndex,documentId,filename,mimeType,sizeBytes}` with strings for stable IDs. SourceDigest is lower-case SHA256 of canonical immutable source. No access hash, fileReference, storage URL or storage key is sent.

Claim renews the worker's existing active job with the same job lease token (180 seconds); otherwise it leases the oldest available job for this exact account/generation, max five attempts. Only one active CV job per owner is offered. Renew the connection heartbeat/lease before every bounded download tick. Mac re-fetches the exact peer/message, verifies document ID plus original filename/size when present, and obtains fresh private Telegram access fields locally. Never substitute another attachment. The download uses bounded <=512KiB chunks, offset accumulation <=4MiB, with timeout/cancellation and exact final size checks. A FILE_REFERENCE_EXPIRED retry re-fetches that same document and keeps already verified bytes only if identity/size still match.

Once all bytes are available, POST /api/telegram-cv/worker/upload with `Content-Type: application/octet-stream`, bearer token, and header `X-Telegram-CV-Proof` containing unpadded base64url UTF-8 JSON of `{...Proof,jobId,jobLeaseToken,sourceDigest,sha256,sizeBytes}`. sha256 is lower-case hex of complete bytes, sizeBytes integer 1–4194304. Header limit 4096 characters, body limit 4194304 bytes. No JSON/base64 file body. Server authenticates and preflights before reading bytes; actual byte count/hash/content signature/filename extension are checked by the host. Claimed hash/size are not trusted for first attachment.

Success receipt: `{ok:true,jobId,draftId,status:"completed",draftVersion,documentRevision,cv:{filename,status:"validated"}}`. A matching committed receipt is checked before expired job-lease rejection but still requires current account/generation proof. Lost upload ACK can replay the same proof/hash/bytes safely. A different committed digest returns409; expired uncommitted lease returns409 and stale bytes must never attach. Storage HTTP requests have a 10-second abort deadline. An expired/claimed cleanup reservation marks the job failed UPLOAD_EXPIRED; explicit retry creates a fresh lease/key. Host reserves a candidate-target-specific random private key before storage I/O, performs no network call while holding a DB transaction, then rechecks all guards before finalizing. Storage retries verify any already-existing reserved object rather than overwriting it. Different drafts referencing the same attachment receive different target keys. Uncertain writes/commits remain reserved for existing cleanup; never delete an object that may be referenced.

Defer JSON `{...Proof,jobId,jobLeaseToken,code,retryAfterSeconds}` → `{ok:true}`. Code `FLOOD_WAIT|TELEGRAM_UNAVAILABLE|SOURCE_CHANGED|SOURCE_UNAVAILABLE|FILE_TOO_LARGE|INVALID_FILE|WORKER_ERROR`; delay integer 1–604800. FLOOD_WAIT does not consume the attempt budget and persists account-wide cooldown shared with history; no sleeping under a lease. TELEGRAM_UNAVAILABLE/WORKER_ERROR become waiting, max five attempts; other codes except FLOOD_WAIT fail immediately for recruiter action. A repeated defer for the same lease/code is idempotent after lost ACK. Host validation400/422 is definitive: worker defers INVALID_FILE, never substitutes another file or empty content. HTTP5xx is uncertain: retain the exact pending bytes and retry; do not delete them on an ambiguous response. On409 fence, discard stale local work and claim current work. On403 stop until credentials/permissions are repaired.

## Storage and decisions

New CV jobs hold the immutable source reference until their disposition is complete. Raw history/source cleanup remains deferred as documented in the extraction checkpoint. A document-change trigger increments documentRevision and cancels active retrievals when a manual CV wins; approval/discard also fences active work. Finalization tests that the draft is open, its document remains null, and its documentRevision equals the captured revision. It increments the normal draft version so browser data refreshes while allowing unrelated field edits during download. Existing manual upload type checks, storage cleanup reservations, signed download access and candidate approval remain authoritative.

Parallel ownership: backend owns this contract, migration20261002170000, pure validators/operations/routes and DB tests; connector owns bounded download/cache/scheduling and worker tests; UI owns explicit selection/progress/retry/cancel and browser tests; root owns release/CI and cross-component storage acceptance. No live Telegram/provider/storage calls are part of local tests.
