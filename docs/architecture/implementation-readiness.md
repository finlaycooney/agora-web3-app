## Foundation migration batch

D03 was approved by the owner on 2026-09-22 for the additive local foundation batch only. The batch adds `supabase/migrations/20260922090000_foundation_roles.sql`, `20260922090100_foundation_schema.sql` and `20260922090200_foundation_seed.sql`.

- The roles migration provisions six NOLOGIN PostgreSQL roles (`app_owner`, `app_staff`, `app_intake`, `app_worker`, `app_executor`, `app_authz_reader`), fails closed on unexpected pre-existing attributes, on any membership held by a foundation role in another role, and on unexpected grantees of `app_owner`/`app_executor`/`app_authz_reader` other than the migration operator. It grants `app_owner` only to the migration operator when needed, and grants `app_owner` CREATE on the current database so it can own the `app` schema. The no-membership constraint is foundation-only; later reviewed credential provisioning may grant deliberate memberships under its own batch.
- The schema migration creates the 16 reviewed foundation tables owned by `app_owner`, with composite same-tenant foreign keys, the specified uniqueness/check constraints and indexes, and enabled + forced RLS on every table. `candidates.current_document_id` and `applications.notice_id` are omitted entirely until the document and privacy batches provide their FK targets (schema specification section 10). No procedures, policies, runtime grants or provider objects exist yet; these deny-all checks are not completed staff authorization. The global `ALTER DEFAULT PRIVILEGES` revoke for functions prevents future objects from inheriting PUBLIC EXECUTE.
- The seed is a versioned bootstrap: the Agora organization, the 21-key permission catalog transcribed from the transaction-contracts matrix, Admin/Recruiter/Viewer roles with the approved initial grants (Viewer seeded inactive) and the default six-stage pipeline. `INSERT ... ON CONFLICT DO NOTHING` protects the catalog and organization; grants and stages are inserted only for roles/pipelines created by that statement, so reruns cannot restore removed grants, recreate deleted stages or overwrite edited names/statuses. Identity collisions on the seeded organization, role key→UUID/`system_kind` bindings and the default pipeline key fail instead of remapping.
- Bootstrap grants carry a null `granted_by_user_id`: the seed runs as the migration/bootstrap principal, which must be able to bypass forced RLS before any policy exists (superusers always can; a non-superuser operator needs BYPASSRLS plus `app_owner` membership granted `WITH INHERIT TRUE, SET TRUE`). Null grant actors are limited to audited migration/bootstrap writes and confer no runtime authority; later grant changes go through the reviewed procedure with a real actor.
- The harness (`tests/database/foundation.test.js`, `tests/support/foundation-docker.js`) guards the environment before mutation: external database/Supabase environment variables and remote Docker endpoints are rejected, all operations verify run- or project-label ownership, Supabase resources are captured by the CLI's `com.supabase.cli.project` label before use, and cleanup removes only captured run-owned identities (volumes by name+`CreatedAt`+label, networks by Id+label, containers by Id+label). `tests/unit/foundation-guard.test.js` covers the pure guards without Docker.
- Catalog assertions inspect effective ACL entries (`aclexplode` over `nspacl`, `relacl`/`acldefault`), not just null-`relacl` heuristics, and include a transactional function probe asserting PUBLIC and runtime roles cannot EXECUTE new `app` functions by default.
- Verification commands: `npm run test:db:foundation` (fresh PostgreSQL 17 and 16 containers) and `FOUNDATION_TEST_MODE=supabase npm run test:db:foundation` (isolated Supabase CLI workdir, legacy upgrade without reset, then the existing backend Playwright suite against the isolated stack only). The first PostgreSQL 17 container carries a synthetic `public.applicants` lock target to prove migrations do not touch the legacy table; a second, truly clean instance proves identical ordered migrations produce an identical schema shape.

## Staff authorization core batch

The owner approved splitting the planned staff/privacy step on 2026-09-22: the authorization core plus the `audit_events` table land now (`supabase/migrations/20260922130000_staff_authorization_core.sql`); privacy procedures remain a dependent PR. This batch adds no staff routes, login, bootstrap identities, candidate data reads or staff table enumeration, and does not modify candidate OAuth or the legacy runtime.

- `app.audit_events` is a forced-RLS tenant table with caller-generated `id`/`correlation_id`, composite tenant-bound actor foreign keys (`(organization_id,actor_membership_id)` and `(organization_id,actor_membership_id,actor_user_id)` against the new `organization_memberships` `(organization_id,id,user_id)` key), a 4 KiB object-capped `details` column and a CHECK allowlisting the two current actions' detail keys. Insert happens only through the executor policy (`staff` actor kind, context-bound actor and membership); no runtime read interface exists yet.
- `app.context_uuid_v1` (STABLE, SECURITY INVOKER, `app_owner`) returns the asserted actor/organization UUID only for the two supported settings with a valid UUID shape.
- `app.has_permission_v1` (STABLE, SECURITY DEFINER, `app_authz_reader`) checks active user, organization, membership and non-viewer role plus a nonretired grant; unknown keys and missing/malformed context return false without leaking detail.
- `app.resolve_staff_principal_v1` (VOLATILE, SECURITY DEFINER, `app_authz_reader`) maps a server-verified `github`/`https://github.com` numeric subject to `user_id`, `membership_id`, `role_id` only when every link is active and non-viewer; it clears all five context settings at entry and before returning so failed resolution cannot retain a prior actor context. It is not a public authentication mechanism — database settings remain trusted server assertions and credential compromise can forge them.
- `app.change_membership_v1` and `app.change_role_grants_v1` (VOLATILE, SECURITY DEFINER, `app_executor`) serialize on an exclusive `FOR UPDATE` lock of the organization row, then re-check `staff.manage`/`roles.manage` after the lock, enforce expected versions, validate statuses/roles/keys, protect the final effective Admin (active user + membership + admin role + all three protected grants) and write one bounded audit row atomically. `app_staff` holds schema USAGE and EXECUTE on the five routines only — no table privileges; `app_intake`, `app_worker`, `anon`, `authenticated` and `service_role` stay denied, and the internal definer roles remain NOLOGIN with no runtime membership.
- `src/lib/staff-authorization.js` is the integration seam (`withStaffTransaction`): it validates the server-verified identity shape, runs one checked-out connection through resolve → context → conjunctive permission checks → callback, mints `auditId`/`correlationId` per call and rolls back on any failure. It is an internal transaction seam, not an authenticator — it expects already authenticated, server-verified assertions; callers must never pass browser JSON as `verifiedIdentity`; the D04 auth/MFA middleware must construct it. Nothing wires it into routes, so real staff access stays disabled.

## Privacy operations core batch

The next approved slice adds `supabase/migrations/20260923140000_privacy_operations_core.sql` and the `src/lib/privacy-operations.js` integration seam — five auditable staff procedures over the privacy data foundation, callable through the existing `withStaffTransaction` context seam under `privacy.manage`. This is a bounded backend workflow for case registration, subject review, verification, candidate correction and subject restriction; it is not the full rights-handling design. No staff routes, login, UI, disclosure execution, outbox/ledger workers or runtime activation are included.

- Public procedures (`SECURITY DEFINER`, owned by `app_executor`, EXECUTE to `app_staff` only, fixed `search_path`): `create_privacy_request_v1(request_id, kind, received_at, due_at, audit_id, correlation_id)`, `review_privacy_subject_v1(request_id, expected_request_version, subject_id, candidate_id, legacy_record_id, expected_target_version, source_sha256, audit_id, correlation_id)`, `verify_privacy_request_v1(request_id, expected_version, verification_method, audit_id, correlation_id)`, `correct_privacy_candidate_v1(request_id, expected_request_version, subject_id, expected_candidate_version, changes, audit_id, correlation_id)` and `restrict_privacy_subject_v1(request_id, expected_request_version, subject_id, expected_target_version, audit_id, correlation_id)`. Internal helpers `privacy_actor_v1`/`privacy_lock_request_v1`/`privacy_record_event_v1` stay `SECURITY INVOKER` owned by `app_owner` with EXECUTE to `app_executor` only.
- Scope and locking: every call asserts the staff actor, `privacy.manage` permission and read-committed isolation via `privacy_actor_v1`, then locks in order — organization row `FOR UPDATE` (serializing against staff membership/grant changes and re-checking authority after the wait), privacy request `FOR UPDATE`, the reviewed candidate or legacy target `FOR UPDATE`, then affected child rows in UUID order. Optimistic request/target versions return 40001; missing or cross-organization records return P0002; invalid workflow states return 23514.
- Columns added: `legacy_records.processing_restricted` and `legacy_records.lifecycle_generation`, plus `privacy_request_subjects.legacy_version` (nullable for historical rows; the procedures re-review and populate it before acting on a legacy target).
- Audit and evidence: each call emits one `privacy_events` row and one `audit_events` row sharing the application-generated `audit_id`; the audit action CHECK was replaced by a named `audit_events_action_check` retaining the two staff actions and allowing the five privacy actions with an identifier/version/scope-only `details` allowlist — no personal values, fingerprints or document text. Duplicate audit IDs roll back the whole operation.
- Correction semantics: canonical candidates only; the reviewed subject, both versions and the candidate lifecycle must still match. Only `full_name`/`professional_summary` may change (string-or-null values; a non-null `full_name` must be nonblank and ≤256 chars, a summary ≤10000 chars; a null clears the stored value; ≤48 KiB payload; at least one real change). Submitted application facts, filenames and blob bytes/metadata are untouched; the request moves to `in_progress` and a fresh review is required before further action. No legacy adapter/snapshot correction is provided.
- Restriction semantics: requires a verified/in-progress request with a matching reviewed subject. A canonical candidate goes `restricted` with bumped lifecycle generation; its active documents and processing purposes are restricted, live/unavailable/retired blob generations advance, and `intended` disclosures are cancelled — sent history is untouched and nothing is deleted. A legacy target gets `processing_restricted` and bumped generation, cancelling only that record's `intended` disclosures; the source `public.applicants` payload is never written. More than 1000 affected child rows fails 54000 for a future worker path. Scopes are `candidate_records_only`/`legacy_metadata_only`; this is local enforcement metadata, not a claim that external recipients, previously issued URLs or privileged service-role paths are contained.
- Access boundary: `app_executor` receives SELECT and INSERT on the required tables plus column-scoped UPDATE privileges, and context+permission-bound RLS policies on the touched tables; `app_staff` keeps procedure-only access — raw table SELECT/DML stays denied, helpers are not executable by staff, and `app_intake`/`app_worker`/provider roles are denied. The internal `app_executor`/`app_authz_reader` roles are inaccessible to runtime callers (the staff credential cannot `SET ROLE` them) and every public procedure additionally requires the trusted actor/organization context. There is no generic candidate CRUD or access/export endpoint, no request fulfillment/rejection and no ledger confirmation path. The five earlier authorization routines are unchanged.
