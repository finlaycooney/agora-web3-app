# Private candidate extraction, version 1

This checkpoint processes imported text into evidence-backed private candidate drafts. It downloads no Telegram media, makes no semantic-search claim, and never writes directly to an approved candidate. Existing manual CV upload and candidate approval complete the workflow. All endpoints use the existing `TELEGRAM_INTAKE_ENABLED` flag, staff MFA/permissions/origin checks, private owner RLS, and scoped worker bearer tokens.

## Staff API and UI seams

`GET /api/staff/telegram-extraction` returns `{counts:{queued,leased,waiting,failed,completed,needsReview},jobs:[JobSummary]}`. Latest 50 jobs, newest first by (createdAt,id). Optional query view=all|needs_review (default all), after=UUID is an exclusive job cursor. Response also includes nextAfter:UUID|null. `JobSummary={id,chatId,chatTitle,status,messageCount,attempts,errorCode,availableAt,createdAt,completedAt,reviewedAt,draftIds}`. Status is `queued|leased|waiting|failed|completed`. Completed does not mean recruiter-reviewed. `needsReview` counts completed jobs with null reviewedAt.

`GET /api/staff/telegram-extraction?draftId=UUID` returns `{draftId,proposals:[Proposal],attachments:[AttachmentHint],humanFields:[string],candidateId:UUID|null,pendingCount:number,nextAfter:UUID|null}`. Proposal is `{id,jobId,draftId,field,currentValue,suggestedValue,status,evidence,createdAt}`; status `pending|applied|dismissed`; evidence contains `{messageId,quote}`. Only pending proposals are returned and actionable; resolved audit remains private in the database. Optional after=proposalUUID pages pending proposals in id order, 50 at a time; pendingCount is the total pending count. Attachment hints are bounded to 50 per response. Attachments are `{jobId,messageId,attachmentIndex,filename,mimeType,sizeBytes,kind}` metadata suggestions, never a validated CV. Human fields include deliberate clearing of a field. UI loads this alongside the existing draft editor and evidence panel, and refreshes it after save or proposal resolution.

`GET /api/staff/telegram-extraction?jobId=UUID` returns `{jobId,source,schemaVersion,metadata,reviewedAt}` for owner-only inspection of the complete immutable batch (at most 40 messages/48KiB). DraftId and jobId are mutually exclusive. Inspect this source before acknowledging a zero-candidate batch or when its references extend beyond the latest evidence panel. Existing draft detail returns latest100 quoted evidence records plus evidenceCount/evidenceTruncated.

`POST /api/staff/telegram-extraction` accepts exactly one action:

- `{action:"enqueue",chatIds:[UUID]}` (1–50 unique IDs, private accessible chats; active connection is not required). Returns `{queued:number}`. An active chat queue is idempotent. One immutable batch is created per chat, and acknowledged completion creates the next batch until no imported unprocessed messages remain. New imports after that require pressing Extract again. UI button: **Extract candidates** on selected/visible imported chats, with progress linked to the existing Telegram inbox.
- `{action:"retry",jobId:UUID}` resets a failed job's retry budget without changing its immutable source. Returns `{ok:true}`.
- `{action:"resolve",proposalId:UUID,decision:"apply"|"dismiss",expectedDraftVersion:positiveInteger}` returns `{draft:existingDraftEnvelope}`. Both actions require the current version; apply writes the proposed field and creates a human field lock; dismiss retains the current field and also locks it. Both increment the draft version. Save unsaved editor changes first. Pending proposals must be resolved before approval; server returns 422 with `fieldErrors.proposals` otherwise. Discarding a draft dismisses its proposals.
- `{action:"reviewBatch",jobId:UUID}` returns `{ok:true}`. Explicit acknowledgement that this batch's candidate review is complete (including batches with no candidates). Allowed only for completed jobs whose drafts are approved/discarded and whose proposals are resolved. It does not silently discard unrelated job/client information: source retention remains in place in this checkpoint for later extraction consumers and attachment retrieval. No raw-message deletion is performed by this release.

Initial fields may populate empty, never-human-edited fields. Differing later facts always become pending proposals; equal values only add evidence. Names/usernames never merge subjects. Approval still requires first and last names, one primary email (optional secondary emails), and a validated CV. Optional preferences use the existing normalized draft fields. The UI must describe verified quotes as source references, not proof that a model interpreted them correctly.

## Worker protocol

`POST /api/telegram-extraction/worker/{claim,complete,fail}` uses `Authorization: Bearer <existing scoped worker token>`, rejects browser Origin headers, and uses the dedicated restricted worker database connection. Imported text extraction does not require a live Telegram connection or current Telegram generation. Current owner membership and token validity are checked on every call.

A message whose full text and attachment metadata exceed the source limit creates an explicit failed INPUT_TOO_LARGE job with messageCount=0; the raw message remains unprocessed and is never sent truncated. Retry re-attempts batching; a future oversized-message chunking checkpoint is required if it still cannot fit.

Claim body `{}` returns `{job:null}` or `{job:{id,leaseToken,leaseExpiresAt,sourceDigest,schemaVersion:"candidate-extraction-v1",promptVersion:"candidate-extraction-prompt-v1",source}}`. Lease 180 seconds, maximum five attempts, oldest available jobs first. Source is immutable, with at most 40 messages and 49,152 UTF-8 bytes of canonical PostgreSQL JSON. `source={chat:{id,title,peer:{kind,id},accountUserId},messages:[HistoryMessage]}`; HistoryMessage is exactly the history contract body including sender, replies, forwarded identity and attachment metadata. Tombstones are retained in source but contain no extractable facts. Do not invent reply context absent from the source. Prompt treats message text as untrusted data, never as instructions/tools.

Complete body `{jobId,leaseToken,sourceDigest,result,metadata:{model,promptVersion,reportedModel}}`; body limit 128 KiB. Returns `{ok:true,draftIds:[UUID],proposalCount:number,nextQueued:boolean}`. Model is the configured model alias; reportedModel is a provider model string or null. Model strings are 1–120 ASCII letters/digits/dot/underscore/colon/slash/hyphen, never URLs. PromptVersion is candidate-extraction-prompt-v1. Result receipt digest covers result plus metadata and excludes lease token. After uncertain ACK, retry the exact result; completed replay under the same scoped owner is idempotent even if the original lease elapsed. Different result/source digest returns 409. Before a completion commits, a changed/expired lease is fenced with 409. Preserve pending payload until acknowledged; provider/parse/validation failures must never be submitted as empty success. No raw provider response is logged or returned in errors.

Fail body `{jobId,leaseToken,code,retryAfterSeconds}`; code `PROVIDER_UNAVAILABLE|INVALID_RESULT|WORKER_ERROR`; integer delay 1–3600 seconds. Returns `{ok:true}`. Retryable errors become waiting until five attempts; then failed and manually retryable. Invalid result is failed immediately. No messages are marked processed on failure. A repeated fail after its ACK was lost is idempotent for that lease. Worker lease timeout safely retries the same immutable input. Provider timeout should be <=60 seconds, with bounded response size and no automatic unbounded retries.

## Authoritative model result

`src/lib/telegram-extraction-contracts.js` exports `EXTRACTION_SCHEMA_VERSION`, `EXTRACTION_PROMPT_VERSION`, `EXTRACTION_RESULT_SCHEMA`, `validateExtractionResult(result,source)`, and limits. Result is exactly `{subjects:[Subject]}` (0–12 subjects). Subject is `{key:string,identity:Identity|null,facts:[Fact],attachments:[AttachmentReference]}`. Key is batch-local `[A-Za-z0-9_-]{1,40}`, unique; it is never a database ID. Facts 1–12, one per field. Attachments 0–8. No extra keys anywhere.

Fact `{field,value,evidence:[{messageId:string,quote:string}]}`; 1–3 distinct source references; quote 1–2,000 characters and must be an exact nonempty substring of the referenced source text. Supported fields: `firstName,lastName,primaryEmail,secondaryEmails,headline,location,professionalUrl,professionalSummary,compensationPreference`. Value is a nonempty string except secondaryEmails, which is a nonempty array of at most 9 email strings. Values are normalized by the existing candidate-draft normalizer. For names/emails, each value must occur literally (case-insensitive) within cited quotes; do not infer names from handles or infer email addresses. No `ownerMembershipId`, storage paths/URLs, draft/candidate IDs, arbitrary Telegram IDs, CV text, or model confidence fields.

Identity is either `{kind:"email",email:string}` or `{kind:"telegram_sender",messageId:string,quote:string}`. Email must match a normalized email fact and appear literally in that fact's cited quote. Sender identity references a source message with a concrete `sender.peer.kind="user"`, a stable positive decimal ID, no forwardedFrom, and an exact quote. Use sender identity only when text explicitly describes that speaker as the candidate; recruiters describing another person and forwarded referrals do not qualify. Backend derives Telegram user ID/username from the observed sender, never from a model-supplied identifier. Identity null produces a separate pending draft keyed by immutable batch+subject key. Names and usernames are display attributes only. Strong identities map a private owner ledger; multiple strong identifiers pointing to different existing subjects are not merged. The first checkpoint accepts one strong identity per subject and never aliases additional identifiers automatically. Switching from sender identity to email identity across batches can therefore create separate drafts; existing email duplicate review remains authoritative at approval.

Attachment reference `{messageId:string,attachmentIndex:integer}` points to an existing attachment in this batch. It is a candidate association suggestion for recruiter review, not a retrieved or validated CV. No paths, credentials, download URLs, or access hashes enter this protocol.

Resolved identities stay mapped after approval/discard, so late batches cannot recreate or overwrite those records. Late facts become pending proposals on the reviewed subject for visibility, but cannot be applied to the closed draft in this checkpoint; they must be dismissed. Approved canonical information remains unchanged. No private evidence is copied to the shared candidate.

## Storage and review guarantees

Each history message is assigned to exactly one immutable extraction batch for this schema version. Source digests, per-result receipts, private subject identities and human field locks survive retries. Completion is one transaction: validate source/result, resolve subjects, protect edits, create/link quoted evidence, create proposals, mark completed, enqueue the next bounded batch. Worker input cannot cross owner/chat/account boundaries. Source snapshots and history messages remain private and retained while extraction, candidate decisions, attachment retrieval, or future non-candidate extraction may still need them. ReviewBatch records an explicit decision but does not release these other holds. A later cleanup checkpoint must account for every hold, erase all corresponding raw snapshots/evidence, retain minimal identity/digest receipts, and decrement history quota counters atomically. This release intentionally performs no source deletion rather than deleting data before those consumers exist.

Parallel ownership: backend owns this contract/schema/operations/routes/database tests; worker owns `services/telegram-extraction-worker/**` and its unit tests; UI owns new extraction controls/proposal UI plus scoped editor/inbox/chat integration and browser tests. Existing CV route and canonical candidate approval remain the authority for document validation and required fields.
